# Vibe-HR Spring Platform

This directory is the Spring Boot 4 / Java 21 target for the incremental Vibe-HR migration. It is a package-by-feature modular monolith: each future business capability owns its HTTP, application, persistence, and mapping code below `com.vibehr.<feature>`. The `platform` package contains cross-cutting HTTP, configuration, and health behavior; `auth` contains migration-compatible authentication primitives.

## Run and verify

```powershell
cd backend-spring
$env:SPRING_DATASOURCE_URL = "jdbc:postgresql://localhost:5432/vibe_hr"
$env:SPRING_DATASOURCE_USERNAME = "postgres"
$env:SPRING_DATASOURCE_PASSWORD = "<local-password>"
$env:AUTH_TOKEN_SECRET = "<openssl-rand-hex-32-output>"
$env:VIBEHR_BFF_ASSERTION_SECRET = "<different-openssl-rand-hex-32-output>"
./gradlew bootRun --args="--spring.profiles.active=local"

./gradlew clean test
./gradlew bootJar
```

Spring reads `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`, and separate `AUTH_TOKEN_SECRET` / `VIBEHR_BFF_ASSERTION_SECRET` values for JWT and BFF HMAC assertions. Both must be distinct 64-character hexadecimal values generated by `openssl rand -hex 32`. The deployed BFF also requires `VIBEHR_BFF_TRUSTED_CLIENT_IP_HEADER=x-vibehr-client-ip`; the loopback-only reverse proxy must overwrite that header with one canonical client IP literal. Do not commit `.env` files or real credentials.

Profiles:

- `application.yml` is the common production-safe baseline: UTC, snake_case JSON, `ddl-auto=validate`, graceful shutdown, ECS console logs, health probes, and the FastAPI-compatible public OpenAPI URLs.
- `local` enables local SQL diagnostics but still requires environment-provided credentials and JWT secret.
- `test` excludes the Docker-backed `integration` tag. It uses neither H2 nor Docker; its health tests supply a test-only controllable `DataSource`.
- `integration` is reserved for Docker-backed Testcontainers checks.
- `flyway-cutover` enables Flyway only after ownership-transfer preconditions are supplied. An `alembic_version` marker is frozen pre-cutover evidence and must be adopted by Spring before Flyway can run.

## Persistence migration rule

Use JPA for aggregate-oriented writes and ordinary entity lifecycle behavior. Use MyBatis only for read projections whose joins, reporting shape, performance characteristics, or migration parity need explicit SQL. A feature owns one primary write path; do not make JPA and MyBatis update the same aggregate in the same transaction.

Flyway is the sole runtime schema and required-reference-data writer and remains disabled outside the explicit cutover profile. The profile requires `VIBEHR_SCHEMA_OWNER=flyway`, validates the checked-in baseline, and rejects unadopted databases. Python/Alembic references are frozen migration evidence, not executable runtime instructions. See `docs/spring-migration/CUTOVER_RUNBOOK.md` before using it.

The reviewed 2026-08-03 production-copy catalog drift has a separate fail-closed `pre-adoption-reconciliation` command profile. It requires an exact confirmation token, Alembic head, source fingerprint, and advisory lock, preserves the original tables in an archive schema, and verifies protected row checksums plus the frozen V1 manifest before commit. See [`PRODUCTION_DRIFT_RECONCILIATION_20260803.md`](../docs/spring-migration/PRODUCTION_DRIFT_RECONCILIATION_20260803.md); do not run it against production without separate approval.

## Public OpenAPI contracts

Springdoc 3.0.3 serves the compatibility paths: `GET` and `HEAD` for `/openapi.json`, `/docs`, `/docs/oauth2-redirect`, and `/redoc`. `/docs` forwards to Swagger UI, and `/redoc` is a lightweight ReDoc page bound to `/openapi.json`.

Run the route and BFF static checks from the repository root:

```powershell
node scripts/spring-migration/spring-route-coverage.js --verify-complete
node scripts/spring-migration/bff-cutover-audit.js
```

## Current security boundary

### Social identity verification

`POST /api/v1/auth/social/exchange` is not public. The Next.js BFF first exchanges the OAuth authorization code with Google or Kakao, fetches the provider profile, and requires the provider's verified-email signal (`verified_email` for Google; both `is_email_valid` and `is_email_verified` for Kakao). It then sends a separate-secret HMAC assertion that binds the provider, provider subject, verified email, display name, HTTP method/path, 30-second lifetime, and a single-use nonce. Spring verifies every claim and consumes the nonce before issuing a Vibe-HR JWT.

This deliberately does not add a provider-identity table to the immutable 105-table migration baseline. The legacy account model identifies the employee account by its canonical verified email, and the one-time assertion proves current control of that email without persisting an unverified external claim. A future requirement to retain provider-subject links, support account linking, or permit an email change must be a separately reviewed Flyway migration with an explicit account-recovery policy.

The platform validates the legacy `pbkdf2_sha256$<positive-iterations>$hexSalt$hexDigest` password format and HS256 JWT claims (`iss`, digit-only `sub`, `iat`, `exp`) against migrated user records. Authentication routes require a BFF assertion or a valid access token as appropriate; unauthenticated protected routes retain the FastAPI-compatible `{"detail":"Not authenticated."}` response with HTTP 401.

`GET /api/v1/health` preserves the FastAPI contract. It executes `SELECT 1` through the configured datasource and returns HTTP 200 with `{ "status", "app", "environment", "db" }`; a failed query returns `status: "degraded"` and `db: "error"`. The root `/health` remains the lightweight operational probe.

422 responses use the FastAPI-shaped `{ "detail": [{ "type", "loc", "msg", "input" }] }` form. Body and method-parameter locations are covered by MVC tests (`body.employee_no`, `query.page`). This is response-shape compatibility only: the full Pydantic error taxonomy and every edge-case error payload are not yet migration-parity guarantees.

## Optional container integration

Normal unit tests do not require Docker. To run the disposable PostgreSQL Testcontainers check after Docker Desktop is running:

```powershell
$env:VIBEHR_RUN_CONTAINER_TESTS = "true"
./gradlew integrationTest
```

`migrationIntegrationTest` exercises the active V1-V5 Flyway chain on disposable PostgreSQL 16, including the immutable 105-table V1 baseline, the current 106-table installation, and replay-store capacity behavior. It is the required schema cutover gate; run it after the integration check and follow [`docs/spring-migration/CUTOVER_RUNBOOK.md`](../docs/spring-migration/CUTOVER_RUNBOOK.md) for an adoption or production cutover. Do not use `clean`, modify migration history, or run Alembic alongside Flyway.

## Container image and smoke test

The Dockerfile follows Spring Boot's layered-jar approach: dependency, loader, snapshot dependency, and application layers are copied separately so dependency layers can remain cached. Build from this directory after the Gradle wrapper is present:

```powershell
docker build -t vibe-hr-spring:local .
```

The image runs as UID 10001, exposes Actuator readiness, and has no Python runtime. Run the disposable PostgreSQL Spring-only compose smoke from the repository root:

```powershell
./scripts/spring-migration/smoke-spring-compose.ps1
```
