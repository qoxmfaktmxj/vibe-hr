# Vibe-HR Security Policy

Status: Active

## Security Boundary

Spring Security is the backend enforcement point. The Next.js BFF forwards authenticated requests but does not replace server-side authorization. The Spring application validates bearer tokens, active-user status, roles, menu permissions, and action permissions for protected endpoints.

## Protected Data

Employee identity, organization records, time records, payroll, severance, welfare, credentials, tokens, and migration metadata are sensitive. Do not log raw values, place them in fixtures, or copy them into task evidence.

## Runtime Rules

- Supply datasource credentials plus distinct `AUTH_TOKEN_SECRET` and `VIBEHR_BFF_ASSERTION_SECRET` values through environment variables. Each secret must be exactly 64 hexadecimal characters generated by `openssl rand -hex 32`.
- Keep Hibernate in validation mode; only Flyway migrations may mutate schema or required reference data.
- Restrict fixture seeding to the explicit local or demo profile gate.
- Expose only the documented health and OpenAPI endpoints without authentication.
- Use `BigDecimal` and explicit rounding tests for financial behavior.
- The public reverse proxy must remove every client-supplied `X-VibeHR-Client-IP` header and set exactly one canonical IP literal before forwarding to the loopback-only Next.js BFF. `VIBEHR_BFF_TRUSTED_CLIENT_IP_HEADER` is fixed to `x-vibehr-client-ip`; missing, malformed, or multi-value headers fail closed before a BFF assertion is signed. Do not use `X-Forwarded-For` or `Forwarded` for this boundary.

## Required Review

Authentication, authorization, secrets, Flyway, payroll, data repair, and deployment work are R3. They require explicit approval, focused Spring tests, PostgreSQL integration coverage where applicable, and documented recovery evidence. Security fixes must include a regression test unless that is infeasible and the reason is recorded.
